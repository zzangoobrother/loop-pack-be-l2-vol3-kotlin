## Q1. 비동기 결제 PG의 본질

**[질문]**
이번 라운드의 PG 시뮬레이터 명세를 다시 보세요:

```
요청 성공 확률 : 60%
요청 지연 : 100ms ~ 500ms
처리 지연 : 1s ~ 5s
처리 결과
  * 성공 : 70%
  * 한도 초과 : 20%
  * 잘못된 카드 : 10%
```

그리고 결제 요청 페이로드에 `callbackUrl` 이 들어갑니다.

질문은 두 개입니다:

1. 이 PG는 **어떻게 동작하는 시스템**인가요? 동기 PG (예: 결제 요청을 보내면 그 응답으로 즉시 "결제 성공/실패"를 받는)와 비교했을 때 **어떤 점이 본질적으로 다른가요**?
2. 이 차이가 **클라이언트(우리 commerce-api)의 결제 처리 흐름 설계에 어떤 영향**을 미칠까요?

명세에서 보이는 "요청 지연"과 "처리 지연"이 분리되어 있다는 점에 주목해서 답해보세요.

**[답변]**
> 1: 동기는 pg 호출후 응답이 오는동안 아무일도 안하고 기다리지만, 비동기는 pg 호출 후 다른 작업을 하면서 pg 가 성공했는지 확인 한다
> 2: 클라이언트가 결제 요청 후 callbackUrl 로 어떤 상태로 응답이 오는지 알 수 있다.

**[후속 질문 Q1-1: 코드 레벨 비동기 vs 시스템 레벨 비동기 분리]**
"동기/비동기"를 코드 호출 모델(CompletableFuture, async/await)로 답했지만, 발제의 "비동기 결제"는 PG 시스템 자체의 동작 패턴이다. RestTemplate(blocking)으로 호출해도 이 PG는 여전히 비동기 결제 PG이다.

다시 명세를 보고 세 가지를 답하기:
1. "요청 지연 100~500ms" 동안 PG에서 일어나는 일과 응답에 담기는 정보
2. "처리 지연 1~5s"의 주체와 결과 전달 경로
3. callbackUrl이 없다면 결제 성공 여부를 어떻게 알 것인가

**[답변]**
> 1: pg 에서 결제 처리가 동작하고, 결제 성공이 호출 될것이다
> 2: 처리 지연은 많은 요청이 왔을 때 지연되는 시간으로 콜백으로 우리한테 결과를 알려줄것이다.
> 3: 결제 상태를 알 수 있는 api 를 호출하면 된다.

**[후속 질문 Q1-2: 명세의 두 가지 성공률 + 콜백 신뢰성]**
세 가지 흔들기:
1. 명세에 "요청 성공 60%"와 "처리 성공 70%"가 따로 있는 이유 — 첫 응답에 진짜 담기는 것은?
2. "처리 지연"이 부하 때문이 아니라면, PG는 그 1~5초 동안 무엇을 하는가? (PG도 외부 의존)
3. Devil's Advocate: 콜백만 있으면 충분한데 왜 상태 확인 API까지 제공하는가?

**[답변]**
> 1: 응답 요청이 온다. 하지만 성공이 60%, 실패가 40% 확률이다.
> 2: 내부에서 순수하게 동작하는 시간
> 3: 콜백에서 오류가 발생할 수 있고, 지연이 발생할 수 있다. [글감]

**[후속 질문 Q1-3: 시나리오 — 그 응답을 받은 순간 무엇을 알 수 있는가]**
세 가지 시나리오 질문:
1. PG 첫 응답 받은 순간 사용자에게 무엇을 보여줄 수 있는가? (a/b/c 중)
2. 콜백이 30분 지나도 안 올 때 — 누가/언제/어떻게 결제 상태를 알아내는가? (Round 5 어떤 개념과 같은가)
3. PG 첫 응답 본문에 무엇이 담겨야 하는가?

**[답변]**
> 1: b
> 2: 클라이언트가 결제 진행중 상태인 db가 존재하면 pg에 상태 확인 api 를 요청한다
> 3: 결제 상태가 있을 거고, 멱등성을 위해 key가 있을것이다.

**[정리: Q1 비동기 결제 PG의 본질]**

핵심 4가지:
1. PG는 두 번 말을 거는 시스템 — 거래 접수 응답(즉시) + 결제 결과 콜백(1~5초 후)
2. 첫 응답은 "결제 결과"가 아니라 "거래 접수 확인" (txId + PENDING 상태)
3. 콜백은 보장되지 않음 → 우리가 능동적으로 조회 (Reconciliation, Round 5 패턴 재사용) [글감]
4. txId는 멱등성의 토대 — 콜백 중복/재시도/상태 조회의 공유 식별자

명세 해석:
- "요청 성공 확률 60%" = PG가 거래 접수 자체를 받아주는 확률 (HTTP 응답 자체가 안 올 수 있음)
- "처리 결과 70/20/10" = 카드사 승인 결과 (PG가 카드사와 통신하는 1~5초 동안 결정됨)

PG 흐름:
```
① 결제 요청 → ② 거래 접수 응답({txId, PENDING}) → ③ PG가 카드사 호출 →
④ 승인 결과 → ⑤ 콜백 (PUSH, 보장 X) → ⑥ 상태 확인 API (PULL, 안전망)
```

## Q2. 결제 도메인 모델링 — 상태와 전이 (진행 중)

**[질문]**
PG의 동작을 이해했으니, 우리 시스템 안쪽 도메인 모델을 설계한다.

질문 ① 결제 상태 모델
- (a) 결제 상태 enum으로 어떤 값들이 필요한가
- (b) 더 이상 변하지 않는 최종 상태(terminal state)는 어떤 것들인가
- (c) 상태 전이는 모두 가능한가? (예: SUCCESS → FAILED, FAILED → SUCCESS)
- 힌트: Round 5 "set 안전 4조건"의 수렴(convergence) 맥락

질문 ② 주문(Order)과 결제(Payment) 관계
- 시나리오: 한도 초과로 실패 → 다른 카드 재시도 → 또 실패 → 또 다른 카드로 성공
- (a) Order : Payment 카디널리티 (1:1 vs 1:N)
- (b) 결제 실패 시 주문은? (롤백/유지/별도 상태)
- (c) 결제 시도 중 주문 상태는?
- 힌트: "결제가 실패하면 주문을 무조건 롤백해야 할까?"

질문 ③ 사용자 응답 시점 (UX vs 시스템)
- 거래 접수 응답을 받은 그 시점에 사용자에게 HTTP 응답을 어떻게 줘야 하는가
- (가) hold하고 콜백 올 때까지 기다림 (1~5초)
- (나) 즉시 "진행 중" 응답 + 별도 채널로 결과 전달
- (다) 또 다른 방식
- 힌트: "주문 상태는 Pending 인데, 사용자는 결제 안내를 받았다"
