PG 흐름:
```

④ 승인 결과 → ⑤ 콜백 (PUSH, 보장 X) → ⑥ 상태 확인 API (PULL, 안전망)
```

**모델 구조:**
```

                  │                  │
                  │                  ├─ txId (PG 거래 식별자)

                  │                  └─ cardInfo, requestedAt, respondedAt
                  │
                  ├─ status (집계 상태)
                  ├─ totalAmount
                  └─ successfulAttemptId (성공한 시도 참조)
```

**Payment.status (집계 단위, 한 방향):**
- IN_PROGRESS (진행 중 — 아직 결정 안 됨)
- SUCCEEDED (한 Attempt라도 성공)
- FAILED (사용자가 포기 / 모든 시도 실패 후 종료)

**PaymentAttempt.status (시도 단위, 한 방향):**
- PENDING (PG에 보냈고 콜백 대기)
- APPROVED (성공)
- LIMIT_EXCEEDED (한도초과)
- INVALID_CARD (잘못된 카드)
- REQUEST_REJECTED (PG가 거래 접수 자체를 거절 — "요청 성공 60%"에서 떨어진 케이스)

**해결되는 문제들:**
1. **txId 관리** — Attempt가 각자 txId를 가짐. Payment는 txId를 직접 갖지 않음
2. **늦은 콜백 무결성** — 콜백은 txId로 해당 Attempt를 찾아 그 Attempt 상태만 갱신. Payment 전체 상태는 영향 안 받음
3. **재시도 UX** — 한도초과/잘못된카드 시 새 Attempt 생성. 기존 Attempt는 그 상태로 영구 보존
4. **상태 무결성** — Attempt도 Payment도 한 방향 전이만 허용. SUCCESS → FAILED 같은 역행 없음
5. **회계/감사** — Attempt 행이 곧 진실의 기록. 별도 이력 테이블 불필요

**도메인 용어:**
- "결제(Payment)" = **이 주문에 대한 결제 의도 전체** (회의에서 "주문 #500 결제 어떻게 됐어?"에 대한 답의 주체)
- "결제 시도(PaymentAttempt)" = **한 번의 PG 호출** (txId 단위)

업계 PG 어그리게이터(토스/포트원 등)의 API 모델도 대체로 이 2-레벨 구조와 일치.

**[정리: Q2-② Order/Payment 라이프사이클 — 일관된 모델 확정]**

**상태 전이도:**
```
Order:   [생성] → WAITING_PAYMENT ──(Payment.SUCCEEDED)──→ CONFIRMED
                                  └─(Payment.FAILED)────→ CANCELED

Payment: IN_PROGRESS ──(어떤 Attempt든 APPROVED)──→ SUCCEEDED
                     ├─(사용자 명시 취소)──────────→ FAILED
                     └─(타임아웃 N분)─────────────→ FAILED

Attempt: PENDING ──→ APPROVED / LIMIT_EXCEEDED / INVALID_CARD / REQUEST_REJECTED
         (각각 한 방향 종결, 다음 Attempt는 새로 생성)
```

**핵심 결정 4가지:**

1. **결제 진행 중 Order = WAITING_PAYMENT**
   - 결제 결과가 확정될 때까지 명시적 대기 상태로 표현
   - 운영/모니터링에서 "결제 대기 주문이 비정상적으로 많다" 같은 신호 포착 가능

2. **Payment.FAILED 발생 사건 = 사용자 명시 취소 OR 타임아웃**
   - **Attempt 한 번 실패 ≠ Payment.FAILED** (이 분리가 재시도 가능성의 토대)
   - Attempt는 즉시 종결되지만, Payment는 "최종 포기 의사가 확인될 때까지" IN_PROGRESS 유지
   - 타임아웃 정책 (예: 30분 동안 SUCCEEDED Attempt 없으면 FAILED) 필요

3. **재고 차감 시점 = 결제 버튼 누름 시점 (= PG 호출과 사실상 동시)**
   - 1번/2번이 실은 같은 시점 (사용자가 (가) 해석 선택 — "주문 생성 = 결제 버튼")
   - 진짜 1번(장바구니 시점 차감)은 티켓팅/공연예매에서만 쓰는 패턴
   - 3번 (콜백 후 차감)은 절대 금지 — "돈은 받았는데 상품이 없음" 사고

4. **재고 복원 = Payment.FAILED 시점**
   - 사용자 명시 취소 OR 타임아웃 시점에 일괄 복원
   - 재시도(새 Attempt) 동안에는 재고 묶여 있음 → 다른 사용자에게 5~30분 손해 발생
   - **선택의 trade-off**: "결제까지 가서 재고 없다고 하는 것"보다 "처음부터 품절 표시"가 낫다는 사용자 판단

**[글감]** "재고를 언제 차감할 것인가" — 시스템 종류별 trade-off (티켓팅 vs 일반 커머스 vs 마켓플레이스)
**[글감]** "Attempt 실패 ≠ Payment 실패" — 재시도 가능성의 도메인 모델링
**[글감]** 타임아웃 정책 설계 — 너무 짧으면 입력 도중 만료, 너무 길면 재고 점유 손해. 적정값은?

## Q2-③. 사용자 응답 시점 (UX vs 시스템)

**[질문]**
이제 진짜 비동기 PG의 핵심 UX 문제다.

사용자가 결제하기 버튼을 누른 순간, 우리 commerce-api는 PG에 결제 요청을 보낸다. PG는 즉시 거래 접수 응답(txId + PENDING)을 돌려준다. 그러나 진짜 결과(SUCCEEDED / LIMIT_EXCEEDED 등)는 **1~5초 후 콜백으로** 도착한다.

사용자에게 HTTP 응답을 **언제, 어떤 내용으로** 줄 것인가?

세 가지 후보:

**(가) 콜백 받을 때까지 HTTP 응답을 hold (1~5초 대기)**
- 사용자에게는 "결제 성공!" 또는 "한도초과!" 같은 최종 결과를 한 번에 보여줌
- HTTP 커넥션을 콜백 시점까지 열어둠

**(나) 즉시 "결제 진행 중" 응답 → 별도 채널로 결과 전달**
- 사용자에게는 일단 "결제 처리 중입니다. 잠시만 기다려주세요" 화면 표시
- 콜백 받으면 별도 메커니즘(폴링 / WebSocket / SSE / Push)으로 결과 전달

**(다) 또 다른 방식**

세 가지 sub-question:

**①** (가)/(나)/(다) 중 어느 것을 고를 것인가? 그리고 이유는?

**②** **(가)의 함정**: 서버 입장에서 HTTP 커넥션 1만 개를 1~5초씩 열어두는 게 어떤 의미인가?
- Spring MVC의 기본 Tomcat 스레드 풀 기본값 200. 동시 결제 1000건이면?
- DB 커넥션, Connection Pool과의 관계는?

**③** **(나)의 함정**: 사용자가 "결제 진행 중" 화면에서 새로고침하거나 뒤로가기 누르면?
- 콜백은 곧 도착할 텐데, 그 결과는 어디로 가야 하나?
- 사용자가 다시 들어왔을 때 "내 결제 어떻게 됐지?"는 어떻게 알 수 있나?
- 힌트: Q1에서 합의한 "콜백은 보장되지 않음 → 능동적 조회 (PULL)" — 이건 사용자 쪽에서도 똑같이 필요

**[답변]**
> ② : hold를 하면 쓰레드 고갈로 다른 서비스에 영향을 줘 에러발생이나 딜레이가 발생하게 된다
> ③-a : 폴링
> ③-b : 진행상태 화면 또는 결과 화면

**[후속 질문 — ③-b 보강 + ③-c/③-d 진행 필요]**

- ③-b 보강: 새로고침이 호출하는 API와 그 응답이 무엇인가? 폴링과 같은 메커니즘(= 결제 상태 조회 API)인가?
- ③-c (i): 사용자가 이탈 후 재방문 시 자기 결제를 식별하려면? (브라우저 세션 사라짐)
- ③-c (ii): 그 결제의 현재 상태를 알려면 어떤 API?
- ③-d-1: 중복 클릭을 어떤 키로 "같은 요청"임을 판정?
- ③-d-2: 이 메커니즘은 Round 5에서 다룬 어떤 개념과 같은가?

**[정리 — Q2-③ 부분 정리]**

**확정된 부분:**
1. **(나) 선택** — 즉시 "진행 중" 응답 + 별도 채널로 결과 전달
2. **(가) 패턴이 안 좋은 이유** = 스레드 고갈 → 결제 외 다른 서비스까지 cascade 영향
3. **결과 전달 메커니즘** = 폴링 (Polling). WebSocket은 오버스펙 (1~5초 단기 대기)

**미확정 (다음 세션 진입점):**
- 결제 상태 조회 API 설계 (PULL 패턴)
- 사용자 이탈/재방문 시나리오 (PULL 원칙의 두 번째 적용 — 사용자↔우리)
- 중복 클릭 방어 → 멱등성(Idempotency) 키 설계 — Round 5와 연결

**[글감 확정]** "외부 의존성의 latency가 우리 throughput을 잠식한다" — Tomcat 스레드 풀 고갈 → cascade failure. 결제 폭주 한 번에 사이트 전체가 마비되는 메커니즘. (Round 6 핵심 운영 통찰 #1)
